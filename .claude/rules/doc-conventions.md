# Doc conventions

- Docs record structure and rules, not counts that a script can recompute (class, icon, test or file counts); compute those with a script. Docs generated by a script (for example `doc/spec/icon-index.md`) may contain the numbers the script writes.
- Docs cite a CSS value by its `--zk-*` variable, not by its resolved value, because a value written next to its variable drifts from the CSS. A literal value belongs only in a token's own definition table (such as the z-index scale), for a value no variable covers (breakpoints, measured results, tolerances, structural sizes ZK or its JS sets), or in an illustrative example.
- Docs name a token by its full `--zk-*` name, never by a nickname or a value ("data-row 52", "button 36/44"). Whoever removes or renames a token searches for its full name; a nickname hides the mention from that search. This also applies to the comments in the token CSS files.
- Docs describe a set of tokens by the rule that defines it and where the source marks its members, not by a list of members. A list copied from the CSS misses the next member added (for example, the off-ladder seeds are the aliases marked `off-ladder` in `tokens/_sizing.css`). An example may name one or two members as long as it reads as an example, not the full list.
- When a script documents its arguments in a `Usage:` block of its header comment (such as `scripts/build-css.js`, `scripts/check-css-dsp.js` and the marble-theme skill scripts), docs name the script and what to run it for, not its arguments, for example "build the zul CSS with `scripts/build-css.js`". An argument list copied into a doc drifts from the script. Before a doc points at such a script, check that its header documents the arguments the reader needs, including environment variables it reads.
  - Agent briefs and prompt strings follow the same rule, but name what the script runs for (for example "run `scripts/build-css.js` for zul"), so the agent can work out the arguments from the header.
  - Gradle and npm commands are not covered: their arguments are recorded nowhere else, so docs keep them in full (for example `./gradlew test --tests … -PmaxParallelForks=1`). An npm script that takes no arguments (`npm run build:icon-catalog`) is cited as is.
- A CSS value's reason is written once, in the comment beside the value in the CSS. A spec (`doc/spec/**`, `doc/contracts/**`) states the rule and may give the reason in one clause; other docs and skills point to the spec instead of restating the mechanism. Theme-independent docs (the zk-component-rules skill) never say which property a theme sets on which component: they state the CSS mechanism and point to `doc/spec/DESIGN.md`. Every restated reason is one more place that drifts when the CSS changes.
- When a change alters a CSS property that docs explain, search `doc/` and `.claude/` for the component (its selector, such as `.z-combobox`, and its bare name) together with the property, and update every hit in the same commit.
