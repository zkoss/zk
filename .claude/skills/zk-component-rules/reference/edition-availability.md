# Edition availability (CE / PE / EE)

ZK ships in three editions. CSS generated for an EE-only component does no harm in a CE build, but the component itself will not render. When designing a theme, decide which editions it targets — that constrains which preview pages can exist.

## Editions and their JARs

| Edition | JAR | Notes |
|---------|-----|-------|
| CE (Community Edition) | `zul.jar`, `zk.jar`, `zkbind.jar` | Open source |
| PE (Professional Edition) | adds `zkex.jar` | Paid; includes extra widgets |
| EE (Enterprise Edition) | adds `zkmax.jar` | Adds large-data and advanced widgets |

## Components by edition

The edition of a component is the jar whose `lang.xml` / `lang-addon.xml` registers it. Each component belongs to its lowest edition:

| Edition | Jar | Registered in |
|---------|-----|---------------|
| CE (all editions) | `zul.jar` | `zul/src/main/resources/metainfo/zk/lang.xml` |
| PE and EE | `zkex.jar` | `../zkcml/zkex/src/main/resources/metainfo/zk/lang-addon.xml` |
| EE only | `zkmax.jar` | `../zkcml/zkmax/src/main/resources/metainfo/zk/lang-addon.xml` |

ZKDoc edition badges can disagree with the registering jar; the jar wins. To check one component, see "Verification" below. To list the components of one jar: `grep -o '<component-name>[^<]*' <lang.xml or lang-addon.xml from the table>`.

- **EE overrides of CE components.** `zkmax` re-declares a few CE components with `<extends>` (grid, listbox, slider, tab, tree) to add molds or behaviour. They stay CE components; the EE part is the extra mold.
- **Internal names.** Some registered names are implementation detail (Idspace, Macro, Nodom, Layoutregion and similar), not public components.
- **Deprecated since 10.3.0.** Hbox, Vbox and Splitter are `@deprecated` since 10.3.0 (`Hbox.java`, `Vbox.java`, `Splitter.java`; use Hlayout, Vlayout and Splitlayout) but are still registered in CE.
- **Loadingbar** is not a registered component: it is a zkmax client widget started through `org.zkoss.zkmax.ui.util.Loadingbar` (EE).

## Where EE/PE adds CSS next to CE

When both CE and EE provide CSS for the same widget (`listbox`, `tree`), the EE file is loaded **in addition to** the CE file; it does not replace it:

- `js/zkmax/sel/css/listbox.css` adds the responsive stacking mode rules (ZK-6110) on top of `js/zul/sel/css/listbox.css`.
- `zkmax/sel/css/tree.css.dsp` is registered in `lang-addon.xml` but has no source file: it is an empty stub generated by `stubPaths` in `scripts/build-css.js`, so the registered `css-uri` does not return 404. EE adds no tree rules (only `listbox.css` exists under `zkmax/src/main/resources/web/js/zkmax/sel/css/`).

Edit the EE file for rules that only apply when EE is present; edit the CE file when both editions must work.

## Implications for theme design

- **CE-only theme**: do not generate CSS for `chosenbox`, `cascader`, `colorbox`, etc. They will silently 404 if requested.
- **EE theme**: assume all components are available; preview pages can reference every component.
- **Preview pages**: a CE-only theme should not have `chosenbox.zul` / `cascader.zul` / `searchbox.zul` in its sidebar.

## Verification

To check which edition a given component requires, search the ZK source:

```bash
grep -r "<component-class>" $ZK_SOURCE/zul/src/main/resources/metainfo/zk/ $ZKCML_SOURCE/zkex/src/main/resources/metainfo/zk/ $ZKCML_SOURCE/zkmax/src/main/resources/metainfo/zk/
```

(`$ZK_SOURCE` is the root of the ZK CE checkout; `$ZKCML_SOURCE` is the root of the zkcml EE checkout, normally `../zkcml`.)

The JAR-relative path tells you the edition.
