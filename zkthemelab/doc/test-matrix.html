The zkthemelab test matrix

The Marble visual suite is a grid. Each spec file is one feature to check, and each ZK component is a row of data that the feature runs over. This page explains how the grid is built, how each feature decides which components it covers, and how a code change is mapped back to the cells that need to run.

ColumnsFile = featureA spec checks one concern (pixels, density, forced colours, focus ring…) across many components. A spec never belongs to one component.
RowsComponent = dataA component enters the grid through its preview page <comp>.zul, a curated list, or a guard fixture under pv/.
CellsTest = one intersectionTitles start with the widget name: navitem — focus outline is drawn, so -g " navitem — " slices one row.

Three ways a feature picks its rows

Scan-driven

The spec reads the preview folder (webapp/web/*.zul) when Playwright collects tests, and makes one test per page.

  • A new component page is covered with no spec edit.
  • Aggregate pages (scripts/aggregate-pages.json) are skipped; they combine many components.
  • Pages a richer spec already owns are skipped to avoid duplicate baselines.

gallery-scan, brand residual scan, compact heights, font-size equivalence, focus-ring scan

Curated list

The spec names its pages: a constant, a list of cases, or one describe per component.

  • Used where each row needs its own script: opening a pop-up, driving a hover, setting a tablet UA.
  • Shared lists live in helpers, such as VARIANT_PAGES in variant-gallery.ts.
  • A new component is not covered until it is added.

screenshot (depth states), tablet, popup-gallery, compact/brand variant gallery, component-theme-variables, forced-colors, hit-target

Guard fixture

One regression, one minimal page under pv/*-guard.zul, one spec and its own Playwright project.

  • The fixture holds only what the fix needs, so the assertion cannot be satisfied by unrelated markup.
  • Each guard must fail with the pre-fix CSS before it is trusted.
  • The issue goes in a tag (@ZK-6131), not in the title.

panel-radius, navbar-popup-title, chosenbox-inplace, a-icon-only, signature-label, input-invalid, …

The columns, grouped by what they ask

Features fall into four layers. A pixel test and a computed-style test catch different failures, so most components sit in more than one layer.

From preview page to verdict

Every cell runs against the same preview server. The page is the fixture; the spec settles it (fonts loaded, transitions off), then either reads computed styles or compares a screenshot with a local baseline.

Baselines are machine-local because the same CSS renders differently on another OS, font set or GPU. The workflow is capture on unedited CSS, edit and rebuild, then compare with the same arguments.

Which cells does my change need?

scripts/select-tests.mjs walks the grid backwards: from changed files to classes, from classes to the pages that render them, from pages to the tests that open those pages. It answers none, partial (one exact command) or full.

Two rows sit outside this mapping on purpose. Aggregate pages are selected only when their own file changes, and a class that is not on any page at rest falls back to its name prefix, then to the CSS file's own component, and otherwise forces a full run.

Adding a cell

  1. Find the column. Put the test in the spec of the feature it exercises. Open a new spec only for a new feature or a guard.
  2. Find the row. Use the component's own preview page when it already shows the state. Otherwise write a minimal pv/*-guard.zul.
  3. Name it for the slice. <widgetName> — <what is checked>, with the issue as a tag.
  4. Register a project in playwright.config.ts with a testMatch, since each project runs only its own file.
  5. Prove it is red, then green. Run it against the pre-fix CSS and see it fail before trusting the pass.
  6. Refresh the index with scripts/build-class-index.mjs when a spec opens a new fixture URL, so the selector can map changes to it.
